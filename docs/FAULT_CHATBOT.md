# Local Faults chatbot

The floating **Ask about faults** button appears on asset detail pages (`/feature/:id`); `/feature` opens S1. It calls the backend's Ollama adapter, separately from the existing part-diagnosis provider. No API key is needed for the default local endpoint.

Start Ollama and install a text model, for example `ollama pull llama3.2:latest`. Set `OLLAMA_BASE_URL=http://127.0.0.1:11434` and `OLLAMA_MODEL=llama3.2:latest` in ignored `server/.env` or `.env.local` if overriding the defaults, then restart `npm run dev:all`. Ollama must run on the backend computer. Keys, if used for a separately configured authenticated endpoint, belong only in `OLLAMA_API_KEY` on the server.

`GET /api/v1/ai/fault-chat/status` checks that Ollama is reachable and the selected model is installed. `POST /api/v1/ai/fault-chat` accepts a bounded, alternating user/assistant history plus optional selected asset, part, fault and saved diagnosis IDs. It reads a fresh database snapshot for every answer. Clients cannot supply replacement sensor context or system instructions.

Context includes up to three matching cases and three guidance passages from the persisted library, resolved repair steps, the selected saved diagnosis, recorded faults and work-order states, current sensor trust and timestamps, the rule catalogue and configured thresholds. Global fault and sensor counts, a complete fault/rule index, and a context-specific sensor directory are included. Detailed readings are limited to 16 sensors, with up to six detailed faults and six rules. Retrieval prioritises explicitly mentioned IDs/assets/rules, the selected asset, untrusted sensors and sensors linked to faults. For a named fault, sensor details are restricted to its linked inputs and explicitly requested sensors. Other details remain available through the sensor and fault registers. The model is instructed to disclose missing evidence and distinguish demo/reference readings from device data. Up to five recent conversation messages are sent with bounded prior-message lengths.

Ollama generates normal text replies. Exact server-known IDs mentioned in the answer become reference links. A model-generated JSON wrapper is also accepted when valid, but is not required during generation. The server rejects incomplete replies and only creates links for server-known identifiers. Unknown references in a structured wrapper are rejected. Exact known IDs mentioned in prose also become source links when a local model omits its citation list. Case and guidance links open a reference drawer with symptoms, steps, outcomes and original sources. Fault/rule links open the register; sensor links open the sensor register. An Ask a follow-up button beside the inline diagnosis opens the chat with the saved diagnosis ID. Greetings and small talk receive brief natural replies without selected fault context. Other replies shorter than 40 characters are retried once within the same request timeout; persistent fragments are rejected. Follow-ups referring to this or it use the selected fault and diagnosis. The loading status reads "Chatbot is responding...". The assistant may provide general repair and prevention advice beyond saved context, clearly labelled as general guidance. Guidance-based examples must not be described as verified field repairs. The chat can explain existing rule findings but has no tools to change readings, rules, faults or work orders. Conversations remain in page memory and are cleared by New chat or navigation away from the asset page.

Provider errors and timeouts remain visible. Offline demo mode explains that the backend is needed; it does not generate a pretend AI answer. The existing per-minute AI rate limit also covers chat requests. The About navigation and Limits link have been removed; old `/about` links redirect to Overview.
